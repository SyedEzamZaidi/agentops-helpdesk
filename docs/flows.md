# Flows

## wf_Triage_LogRoutingDecision

Agent flow called by the Triage agent once per request, right after classification. Writes one Agent Decision row and returns its ID so later steps (ServiceNow, Remediation) can update or link to the same row.

**Tool on the agent:** `wf_Triage_LogRoutingDecision_v2` · credentials: maker-provided · connection runtime: embedded (see [D17](decisions.md#d17-audit-writes-run-on-the-automations-identity-not-the-users), [D18](decisions.md#d18-verify-connection-runtime-mode-in-the-solution-before-every-deployment)).

### Inputs

| Input | Type | Filled by | Internal key |
|---|---|---|---|
| RequestSummary | Text | AI | `text` |
| Category | Text, fixed list: Knowledge, Ticket, Remediation, Status Check, Escalate | AI | `text_2` |
| RoutingReason | Text | AI | `text_3` |
| RequesterEmail | Text | `System.User.Email` | `text_4` |
| ConversationId | Text | `System.Conversation.Id` | `text_1` |

Internal keys follow creation order, not display order; expressions reference the key.

### Steps

1. **When an agent calls the flow**
2. **Dataverse – Add a new row** (Agent Decisions)

   | Column | Value |
   |---|---|
   | Name | RequestSummary |
   | Request Summary | RequestSummary |
   | Category | Category label mapped to the choice value (below) |
   | Routing Reason | RoutingReason |
   | Requester Email | RequesterEmail |
   | Conversation ID | ConversationId |
   | Handled By | Triage |

3. **Respond to the agent** → `DecisionId` (Text) = the new row's `ezm_agentdecisionid`

### Category mapping

| Label | Choice value |
|---|---|
| Knowledge | 791760000 |
| Ticket | 791760001 |
| Remediation | 791760002 |
| Status Check | 791760003 |
| Escalate (and any unexpected value) | 791760004 |

```
if(equals(triggerBody()?['text_2'],'Knowledge'),791760000,
if(equals(triggerBody()?['text_2'],'Ticket'),791760001,
if(equals(triggerBody()?['text_2'],'Remediation'),791760002,
if(equals(triggerBody()?['text_2'],'Status Check'),791760003,791760004))))
```

Unknown values fall through to Escalate, so a bad classification is routed to a human rather than dropped.

## wf_Common_UpdateDecision

Shared flow that records how a request ended. Called by the specialist agents (Knowledge, ServiceNow) and by deterministic topics; updates the request's existing Agent Decision row instead of creating a new one (one row per request, D24). Built in the classic designer; no expressions.

**Tool on the agent:** `workflow_Common_UpdateDecision` · when used: only when referenced by topics or agents (`triggerCondition: false`), so the orchestrator never calls it on its own · credentials: maker-provided · connection runtime: embedded.

### Inputs

| Input | Type | Notes | Internal key |
|---|---|---|---|
| ConversationId | Text | `System.Conversation.Id` (bound on the tool), used to find the row; never generated by the AI | `text` |
| HandledBy | Text, fixed list: Knowledge, ServiceNow, Remediation, Escalation | Set by the calling topic | `text_1` |
| Outcome | Text, fixed list: Answered, Ticket Created, Remediated, Escalated, Failed, Resolved (self-service), Not found | Set by the calling topic (e.g. the feedback button pressed) | `text_2` |
| SourceArticle | Text, optional | KB article cited by the Knowledge agent | `text_3` |
| IncidentNumber | Text, optional | ServiceNow incident number | `text_4` |

### Steps

1. **Initialize variables** `HandledByValue`, `OutcomeValue` (Integer).
2. **Switch on HandledBy** / **Switch on Outcome**: one case per label, each setting the choice value. Default terminates the run as Failed (`InvalidHandledBy` / `InvalidOutcome`) so an unknown value never reaches the row.
3. **Find latest decision**: List rows, `ezm_conversationid eq '<ConversationId>'`, sorted `createdon desc`, 1 row.
4. **Apply to each** (one row):
   - **Update decision**: Handled By, Outcome.
   - **If SourceArticle passed** → update Source Article.
   - **If IncidentNumber passed** → update Incident Number.
   Optional fields are written only when passed, so one caller never blanks a value set by another.
5. **Respond to the agent** → `Status` = Updated.

### Choice values

| Handled By | Value | Outcome | Value |
|---|---|---|---|
| Triage | 791760000 | Answered | 791760000 |
| Knowledge | 791760001 | Ticket Created | 791760001 |
| ServiceNow | 791760002 | Remediated | 791760002 |
| Remediation | 791760003 | Escalated | 791760003 |
| Escalation | 791760004 | Failed | 791760004 |
| | | Resolved (self-service) | 791760005 |
| | | Not found | 791760006 |

### Unit test (07 Oct 2026)
Inputs: an existing conversation, HandledBy = ServiceNow, Outcome = Ticket Created, IncidentNumber = INC0000TEST, SourceArticle empty. Result: Handled By and Outcome updated, Incident Number set, Source Article and all Triage fields unchanged. The first run left Handled By and Outcome unchanged because the two choice fields were not mapped in *Update decision*; caught by the isolated test before the flow was attached to any agent.

### Defect found in integration (07 Oct 2026)
**Symptom:** first call from the Knowledge Feedback topic failed in the agent with `FlowActionBadGateway / NoResponse`. Run history: *Update a row* rejected `ezm_handledby = 0` (outside the valid range).
**Diagnosis:** the trigger received exactly `Knowledge`, so the caller was cleared. Every case in the HandledBy Switch was skipped: the case value was `Knowledge ` (trailing space), and Switch matching is exact. `HandledByValue` kept its initial 0. The Default branch did not stop the run, so the 0 reached Dataverse and surfaced as a Dataverse validation error instead of the flow's own `InvalidHandledBy`.
**Fix:** trailing space removed; all eleven case values checked in Peek code; Terminate (Failed) in both Default branches.
**Lesson:** the unit test exercised one of the four HandledBy paths. Each case of a mapping Switch needs a test, and a guard branch is only real once a test has hit it.

## wf_Remediation_SubmitRequest

Agent flow called by the *Request Account Fix* topic. Records the request; it never changes an account (D29). Built in the classic designer inside the solution; no expressions.

### Inputs

| Input | Type | Filled by | Notes |
|---|---|---|---|
| ActionCode | Text, fixed list: UNLOCK_ACCOUNT, RESET_MFA, ENABLE_VPN_ACCESS | AI (constrained) | Which catalog fix |
| TargetUserEmail | Text | AI | Whose account the fix is for |
| RequesterEmail | Text | `System.User.Email` | Signed-in user |
| ConversationId | Text | `System.Conversation.Id` | Finds the request's Agent Decision row |

### Steps

1. **Initialize variables** `ActionCodeValue` (Integer), `RequestNumber` (String).
2. **Switch for Action Code** on the input: UNLOCK_ACCOUNT → 791760000, RESET_MFA → 791760001, ENABLE_VPN_ACCESS → 791760002. Default: Terminate (Failed, `InvalidActionCode`).
3. **Find Catalog Fix**: List rows, Remediation Catalog, `ezm_actioncode eq <ActionCodeValue> and ezm_active eq true`, 1 row. An inactive fix returns nothing, so no request is created (allow-list, D5).
4. **Find Latest Decision**: List rows, Agent Decisions, `ezm_conversationid eq '<ConversationId>'`, `createdon desc`, 1 row.
5. **For Catalog → For Decision Row** (nested, one row each):
   - **Create Remediation Request**: Fix = `ezm_remediationcatalogs(<catalog id>)`, Agent Decision = `ezm_agentdecisions(<decision id>)`, Requester Email, Target User Email, Request Status = Pending Approval.
   - **Remember Request Number**: `RequestNumber` = the new row's Request Number.
   - **Mark Handled By Remediation**: update the Agent Decision row, Handled By = Remediation.
6. **Respond to the agent** → `RequestNumber` (empty when the fix is inactive or no decision row exists; the topic treats empty as "could not submit").

The loops are nested because the request row needs both IDs at once; each List rows returns a list even for one row.

### Unit test (16 Oct 2026)
Inputs: ENABLE_VPN_ACCESS, requester = target = the test user, an existing conversation ID. Result: Remediation Request created (Fix = Enable VPN access, linked to the Agent Decision row, Pending Approval); the decision row's Handled By changed to Remediation; other decision fields unchanged.

## wf_Remediation_ProcessRequest

Automated cloud flow that applies the rules, runs the approval and executes the fix. It is not a tool on any agent: the only way to start it is a new Remediation Request row, so the agent can request a change but never make one (D29). Runs on its own connections (Dataverse, Office 365 Users, Approvals, Microsoft Entra ID, Teams), all through connection references; in Test and Prod they map to a service account that owns only the `VPN-Users` group.

**Trigger:** Dataverse, *When a row is added*, Remediation Requests, scope Organization. Added only, so the flow's own status updates never re-trigger it.

### Steps

1. **Get Catalog Fix**: Get a row by ID, Remediation Catalog, Row ID = the request's Fix (Value). The rules are read from the catalog row, not copied onto the request (policy as data, D5).
2. **RejectReason** (String, empty). Every rule writes its reason here; one gate at the end decides.
3. **Rule Self Service**: Self Service Only = true and Requester Email ≠ Target User Email → "This fix can only be requested for your own account."
4. **Get requester profile** (Office 365 Users) → **Rule Department**: Eligible Departments not empty and does not contain the requester's Department → "Your department is not eligible for this fix."
5. **Passed Rules** (RejectReason empty) → **Needs Approval** (Requires Approval = true) → **Get manager (V2)** → **Manager Approval** (Approve/Reject, first to respond, reassignment off) → **Approved** (Outcome = Approve); otherwise RejectReason = "Your manager did not approve this request."
6. **Ready To Run** (RejectReason still empty):
   - **Is VPN Fix** (Action Code = 791760002):
     - Get Target Profile → **Add To VPN Group** (Entra ID, group `VPN-Users`, user = target) → request **Succeeded** ("Added to VPN-Users") → decision Outcome **Remediated** → Teams notification.
     - Other fixes (unlock, MFA reset): request **Failed** ("Automated execution for this fix is not enabled yet.") → decision **Failed** → Teams notification that the service desk will complete it.
   - Otherwise: request **Rejected** with RejectReason as Run Result → decision **Failed** → Teams notification with the reason.

Yes/No and number comparisons use expression values (`true`, `791760002`) because a value typed into a condition is compared as text.

### End-to-end test (17 Oct 2026)
Two requests from the test pane (`I need VPN access on my laptop`): both passed self-service and department rules (Engineering) and waited at Manager Approval. The manager approved one and rejected the other.
- Approved: requester added to `VPN-Users`, request Succeeded, decision Remediated.
- Rejected: request Rejected with the manager reason, decision Failed.

Notes from the test: approvals live in the flow's environment, so the approver needed access to the Dev environment (Basic User) to see them in the Power Automate portal; security defaults required MFA registration for the test approver. Teams notifications could not be viewed in the lab tenant (no Teams licence).
